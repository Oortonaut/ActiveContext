# Context Application Protocol (CAP) -- Protocol Semantics

> Normative specification for the Context Application Protocol, version 1.0.

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
"SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this
document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

---

## 1. Overview

The **Context Application Protocol (CAP)** defines the message semantics for
communication between a host application and one or more plugin servers. CAP
enables plugin servers, written in any language, to provide custom context
node types to the host's context graph.

### 1.1 Architecture

CAP follows a client-server model with two participants:

- **Host**: The application that manages the context graph, projection engine,
  and agent loop. The host connects to plugin servers (either by spawning them
  or connecting to external processes), drives the tick cycle, and owns the DAG
  of context nodes. In ActiveContext, the Session is the host.

- **Plugin Server**: A separate process that implements one or more node types.
  The server responds to host requests, manages node instances internally, and
  MAY push notifications to the host when node state changes asynchronously.

Communication is bidirectional: the host sends requests and notifications to
the server, and the server MAY send push notifications and reverse requests
back to the host.

### 1.2 Design Goals

1. **Language independence** -- Plugin servers MAY be implemented in any
   language that can read and write the message format.
2. **Transport independence** -- This specification defines abstract message
   semantics. The encoding and framing are defined by transport bindings
   (see Section 1.3).
3. **Sync-on-tick** -- State synchronization is batched to tick boundaries,
   minimizing round trips in the hot path.
4. **Schema-driven** -- Node types are fully described by machine-readable
   schemas, enabling code generation, validation, and LLM documentation.
5. **Minimal surface** -- The protocol comprises 12 message types organized
   into four categories.

### 1.3 Transport Binding

This specification is transport-independent. The reference transport binding
uses JSON-RPC 2.0 with newline-delimited framing over stdio pipes (UTF-8
encoded). Other transport bindings (e.g., WebSocket, HTTP) MAY be defined in
separate documents.

When this specification shows wire examples, they use the JSON-RPC 2.0
binding for concreteness.

## 2. Terminology

| Term | Definition |
|------|------------|
| **Host** | The application that owns the context graph and drives the tick cycle. Connects to plugin servers (spawned or external). |
| **Plugin Server** | A separate process providing one or more node types via CAP. |
| **Node** | An instance of a node type in the context graph. Nodes produce rendered content, expose properties, and have lifecycle methods. |
| **Node Type** | A class of nodes with a shared schema (constructor, properties, methods). Identified by a unique string (e.g., `"shell"`, `"topic"`). |
| **Node ID** | A unique string identifying a node instance. Assigned by the host or generated by the server. Stable for the node's lifetime. |
| **Session** | A host-side execution context with its own graph, timeline, and message history. Identified by a session ID string. |
| **Tick** | A discrete synchronization point driven by the host. All state materialization occurs at tick boundaries. |
| **Dirty Flag** | A one-bit signal indicating a node's state has changed and requires synchronization on the next tick. |
| **Render** | A text representation of a node at a specific granularity level (header, content, or detail). |
| **Projection** | The host's token-budgeted composition of rendered nodes for LLM consumption. |
| **DSL** | The Python-based domain-specific language through which the agent manipulates context nodes. |
| **Root** | A filesystem path exposed to the plugin server, akin to a workspace root. |
| **Capability** | A feature flag exchanged during initialization, enabling optional protocol features. |
| **Method Call** | An invocation of a method on a node instance (e.g., `set_content`, `cancel`). |

## 3. Connection Lifecycle

A CAP connection progresses through four phases: startup, handshake, normal
operation, and shutdown. The host is responsible for managing all phase
transitions.

### 3.1 Server Startup and Connection Models

CAP supports two connection models:

- **Host-managed process**: The host spawns the plugin server as a child
  process and owns its lifecycle (start, monitor, terminate). This is the
  common case for single-host deployments.

- **External process**: The host connects to a plugin server that was started
  independently (e.g., a shared server, a system service, or a server managed
  by an orchestrator). The host does NOT own the server's process lifecycle.

In both models, the host MUST establish a transport connection before sending
any messages. The server MUST begin reading from its input immediately upon
becoming reachable.

The connection begins in the `DISCONNECTED` state.

```
State machine:

    DISCONNECTED  ─── connect() ───►  CONNECTING
    CONNECTING    ─── handshake ok ──► CONNECTED
    CONNECTING    ─── handshake fail ► ERROR
    CONNECTED     ─── disconnect() ──► DISCONNECTED
    ERROR         ─── disconnect() ──► DISCONNECTED
```

### 3.2 Initialize Handshake

After starting the server process, the host MUST send an `initialize` request
as the first message. No other messages SHALL be sent before the initialize
handshake completes.

**Host sends:**

```json
{
  "jsonrpc": "2.0",
  "method": "initialize",
  "id": 1,
  "params": {
    "protocol_version": "1.0",
    "host_capabilities": {
      "create_node": true,
      "invoke": true,
      "roots": true,
      "notifications": true
    },
    "roots": [
      {
        "uri": "file:///home/user/project",
        "name": "cwd",
        "description": "Current working directory"
      }
    ],
    "session_id": "sess_abc123",
    "cwd": "/home/user/project"
  }
}
```

**Server responds:**

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "server_name": "my-plugin",
    "server_version": "0.1.0",
    "protocol_version": "1.0",
    "server_capabilities": {
      "sync": true,
      "immediate_call": false,
      "push_dirty": true,
      "push_notifications": true
    },
    "node_types": [
      {
        "node_type": "custom_view",
        "description": "A custom file view with annotations",
        "constructor": { "positional": [], "variadic": null, "named": [] },
        "properties": [],
        "methods": []
      }
    ]
  }
}
```

The server MUST include `server_name` in its response. All other fields have
defaults and are OPTIONAL.

If the server does not support the requested `protocol_version`, it SHOULD
return its own supported version in `protocol_version`. The host MUST check
version compatibility and MAY disconnect if versions are incompatible.

After a successful handshake, the connection transitions to `CONNECTED`.
The host MUST register all node types from the `node_types` array before
accepting DSL calls that reference those types.

### 3.3 Normal Operation

Once connected, the host and server exchange messages according to the
categories defined in Section 4. The host drives the tick cycle and sends
synchronization requests. The server responds to requests and MAY push
notifications.

### 3.4 Graceful Shutdown

Shutdown proceeds in three phases: notification, drain, and cleanup.

#### 3.4.1 Shutdown Notification

The host MUST send a `shutdown` notification to the server as the first step.
This is a one-way notification — no response is expected.

```json
{
  "jsonrpc": "2.0",
  "method": "shutdown"
}
```

After sending the `shutdown` notification, the host MUST NOT send any further
requests or notifications to the server. Any pending requests (awaiting
responses) SHOULD be failed locally with a transport error.

#### 3.4.2 Server Drain

The server MUST begin cleanup upon receiving the `shutdown` notification.
The server MUST NOT send new requests to the host after receiving `shutdown`.
The server SHOULD complete any in-flight responses before exiting, but
MUST NOT begin new work.

For host-managed processes, the server SHOULD exit promptly after cleanup.

For external processes, the server SHOULD close its end of the transport
connection but MAY continue running to serve other hosts.

#### 3.4.3 Transport and Process Cleanup

After sending the shutdown notification and allowing a drain period, the host
MUST close all transport resources (pipes, sockets, channels) associated with
this connection regardless of the connection model.

**Host-managed processes** — If the host spawned the server process, the host
SHOULD wait for the process to exit within a reasonable timeout (RECOMMENDED:
5 seconds). If the server does not exit within the timeout, the host SHOULD
terminate the process forcefully (SIGTERM, then SIGKILL or platform
equivalent). The host MUST NOT attempt to terminate processes it did not spawn.

**External processes** — If the host connected to an externally-managed server,
the host MUST close the transport connection but MUST NOT attempt to terminate
the server process. The server's lifecycle is managed by whoever started it.

#### 3.4.4 Unclean Shutdown

If the transport connection is lost unexpectedly (EOF, broken pipe, connection
reset), both sides MUST treat this as an unclean shutdown:

- The **host** MUST fail all pending requests with a transport error, close
  all transport resources, and transition to `DISCONNECTED`. For host-managed
  processes, the host SHOULD terminate the orphaned process if it is still
  running.

- The **server** SHOULD release resources and, for host-managed processes,
  exit. For external processes, the server MAY remain running and accept
  new connections.

After shutdown completes (clean or unclean), the connection transitions to
`DISCONNECTED`.

## 4. Message Categories

CAP defines 12 message types organized into four categories based on direction
and purpose.

| Category | Direction | Messages |
|----------|-----------|----------|
| Lifecycle | Host -> Server | `initialize`, `shutdown` |
| Node Management | Host -> Server | `node/create`, `node/sync`, `node/call`, `node/destroy`, `node/serialize` |
| Push Notifications | Server -> Host | `node/dirty`, `node/notification` |
| Host API | Server -> Host | `host/create_node`, `host/invoke`, `host/query_roots`, `host/resolve_root` |

Messages with `id` fields are requests that expect responses. Messages without
`id` fields are notifications that expect no response.

### 4.1 Lifecycle Messages

#### 4.1.1 `initialize` -- Handshake

**Direction:** Host -> Server (request)

**Method:** `"initialize"`

Initiates the connection handshake. MUST be the first message sent. The host
declares its capabilities and provides filesystem roots. The server responds
with its capabilities and node type schemas.

**Params (InitializeParams):**

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `protocol_version` | string | No | `"1.0"` | Protocol version the host supports. |
| `host_capabilities` | HostCapabilities | No | all `true` | Capabilities the host offers. |
| `roots` | RootInfo[] | No | `[]` | Filesystem roots available to the server. |
| `session_id` | string | No | `""` | Session identifier for logging and coordination. |
| `cwd` | string | No | `""` | Working directory for the session. |

**Result (InitializeResult):**

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `server_name` | string | **Yes** | -- | Human-readable server name. |
| `server_version` | string | No | `""` | Server version string. |
| `protocol_version` | string | No | `"1.0"` | Protocol version the server supports. |
| `node_types` | NodeTypeSchema[] | No | `[]` | Node types this server provides. |
| `server_capabilities` | ServerCapabilities | No | defaults | Capabilities the server declares. |

**Errors:**

The server SHOULD return a JSON-RPC error if initialization fails. The host
MUST treat initialization failure as a connection error and transition to the
`ERROR` state.

#### 4.1.2 `shutdown` -- Graceful Shutdown

**Direction:** Host -> Server (notification)

**Method:** `"shutdown"`

Notifies the server that the host is ending this connection. This is a
notification (no `id`, no response expected).

Upon receiving `shutdown`, the server MUST:
1. Stop accepting new work for this connection.
2. Complete any in-flight responses.
3. Close its end of the transport.
4. For host-managed processes: exit promptly.
5. For external processes: release connection resources but MAY continue
   serving other hosts.

The host MUST NOT send any messages after `shutdown`. See Section 3.4 for
the full shutdown sequence including transport cleanup and process lifecycle.

**Params:** None.

```json
{
  "jsonrpc": "2.0",
  "method": "shutdown"
}
```

### 4.2 Node Management Messages

These messages manage the lifecycle and state of node instances. All are
requests from the host to the server.

#### 4.2.1 `node/create` -- Create Node Instance

**Direction:** Host -> Server (request)

**Method:** `"node/create"`

Creates a new node instance of the specified type. The host MAY assign a
node ID; if it does, the server MUST use that ID. If no ID is provided,
the server MUST generate a unique ID and return it.

**Params (NodeCreateParams):**

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `node_type` | string | **Yes** | -- | Type of node to create (must match a registered schema). |
| `args` | Any[] | No | `[]` | Positional constructor arguments. |
| `kwargs` | object | No | `{}` | Keyword constructor arguments. |
| `node_id` | string | No | `""` | Host-assigned node ID. If empty, server generates one. |

**Result (NodeCreateResult):**

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `node_id` | string | **Yes** | -- | Node instance ID (assigned or generated). |
| `state` | object | No | `{}` | Initial serialized node state. |
| `renders` | object | No | `{}` | Initial renders (keys: `"header"`, `"content"`, `"detail"`). |
| `tokens` | object | No | `{}` | Initial token estimates (keys: `"collapsed"`, `"summary"`, `"detail"`). |
| `digest` | object | No | `{}` | Initial digest metadata. |

**Wire example:**

```json
// Request
{
  "jsonrpc": "2.0",
  "method": "node/create",
  "id": 2,
  "params": {
    "node_type": "shell",
    "args": ["pytest", "-v"],
    "kwargs": {"timeout": 120},
    "node_id": "shell_a1b2c3d4"
  }
}

// Response
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "node_id": "shell_a1b2c3d4",
    "state": {"command": "pytest -v", "exit_code": null, "is_complete": false},
    "renders": {
      "header": "[SHELL] pytest -v [RUNNING]",
      "content": "",
      "detail": ""
    },
    "tokens": {"collapsed": 12, "summary": 0, "detail": 0},
    "digest": {"type": "shell", "status": "running"}
  }
}
```

**Errors:**

| Error Code | Condition |
|------------|-----------|
| `NODE_TYPE_UNKNOWN` (-32001) | The `node_type` is not registered on this server. |
| `NODE_CREATE_FAILED` (-32005) | Creation failed (invalid args, resource error, etc.). |
| `INVALID_PARAMS` (-32602) | Arguments do not match the constructor schema. |

#### 4.2.2 `node/sync` -- Synchronize Node State

**Direction:** Host -> Server (request)

**Method:** `"node/sync"`

The primary synchronization message. Sent once per tick for each dirty node.
Delivers batched method calls and retrieves the complete node state, renders,
token estimates, digest, and any pending notifications.

This is the **hot path** of the protocol. See Section 5 for the sync-on-tick
model.

**Params (NodeSyncParams):**

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `node_id` | string | **Yes** | -- | Node to synchronize. |
| `calls` | PendingCall[] | No | `[]` | Method calls to execute before returning state. |
| `cwd` | string | No | `""` | Working directory for render methods. |

Each PendingCall has the following shape:

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `method` | string | **Yes** | -- | Method name (e.g., `"set_content"`, `"cancel"`). |
| `args` | Any[] | No | `[]` | Positional arguments. |
| `kwargs` | object | No | `{}` | Keyword arguments. |

**Result (NodeSyncResult):**

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `state` | object | No | `{}` | Full serialized node state (all public fields). |
| `renders` | object | No | `{}` | Rendered content: `"header"`, `"content"`, `"detail"`. |
| `tokens` | object | No | `{}` | Token estimates: `"collapsed"`, `"summary"`, `"detail"`. |
| `digest` | object | No | `{}` | Compact digest metadata. |
| `notifications` | Notification[] | No | `[]` | Notifications generated since last sync. |

Each notification has the shape:

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `description` | string | **Yes** | -- | Human-readable description of what changed. |
| `level` | string | No | `"hold"` | Notification level: `"ignore"`, `"hold"`, or `"wake"`. |

**Wire example:**

```json
// Request
{
  "jsonrpc": "2.0",
  "method": "node/sync",
  "id": 5,
  "params": {
    "node_id": "shell_a1b2c3d4",
    "calls": [
      {"method": "cancel", "args": [], "kwargs": {}}
    ],
    "cwd": "/home/user/project"
  }
}

// Response
{
  "jsonrpc": "2.0",
  "id": 5,
  "result": {
    "state": {"command": "pytest -v", "exit_code": -15, "is_complete": true},
    "renders": {
      "header": "[SHELL] pytest -v [CANCELLED]",
      "content": "Process cancelled by user.",
      "detail": "Exit code: -15\nRuntime: 3.2s"
    },
    "tokens": {"collapsed": 12, "summary": 8, "detail": 20},
    "digest": {"type": "shell", "status": "cancelled", "exit_code": -15},
    "notifications": [
      {"description": "Shell cancelled: pytest -v", "level": "wake"}
    ]
  }
}
```

**Processing semantics:**

1. The server MUST execute all `calls` in array order.
2. If a call fails, the server SHOULD continue processing remaining calls
   and report the error in the response (e.g., via a notification or error
   state in the `state` field).
3. After all calls are processed, the server MUST return the complete current
   state, renders, tokens, and digest.
4. The `renders` object MUST contain `header`, `content`, and `detail` keys.
   Any key MAY map to an empty string if that level has no content.

**Errors:**

| Error Code | Condition |
|------------|-----------|
| `NODE_NOT_FOUND` (-32000) | No node with the given ID exists on this server. |
| `METHOD_NOT_AVAILABLE` (-32002) | A method in the `calls` array is not defined on this node type. |

#### 4.2.3 `node/call` -- Immediate Method Call

**Direction:** Host -> Server (request)

**Method:** `"node/call"`

Executes a method on a node immediately, outside the tick cycle. This is used
for urgent operations where the DSL needs a return value without waiting for
the next tick.

This message requires the `immediate_call` server capability. The host MUST
NOT send `node/call` if the server did not declare `immediate_call: true`.

**Params (NodeCallParams):**

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `node_id` | string | **Yes** | -- | Node to call method on. |
| `method` | string | **Yes** | -- | Method name. |
| `args` | Any[] | No | `[]` | Positional arguments. |
| `kwargs` | object | No | `{}` | Keyword arguments. |

**Result (NodeCallResult):**

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `result` | Any | No | `null` | Return value of the method call. |
| `state_changed` | boolean | No | `false` | Whether the call changed node state (triggers sync on next tick). |

**Wire example:**

```json
// Request
{
  "jsonrpc": "2.0",
  "method": "node/call",
  "id": 8,
  "params": {
    "node_id": "custom_e5f6g7h8",
    "method": "get_summary",
    "args": [],
    "kwargs": {"max_tokens": 200}
  }
}

// Response
{
  "jsonrpc": "2.0",
  "id": 8,
  "result": {
    "result": "Authentication module: 3 endpoints, 2 middleware functions.",
    "state_changed": false
  }
}
```

If `state_changed` is `true`, the host SHOULD mark the node as dirty and
include it in the next tick's sync cycle.

**Errors:**

| Error Code | Condition |
|------------|-----------|
| `NODE_NOT_FOUND` (-32000) | No node with the given ID exists. |
| `METHOD_NOT_AVAILABLE` (-32002) | The method is not defined on this node type. |
| `INVALID_PARAMS` (-32602) | Arguments do not match the method schema. |

#### 4.2.4 `node/destroy` -- Destroy Node Instance

**Direction:** Host -> Server (request)

**Method:** `"node/destroy"`

Destroys a node instance. The server MUST release all resources associated
with the node. After destruction, the node ID MUST NOT be reused for new
nodes within the same connection.

**Params (NodeDestroyParams):**

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `node_id` | string | **Yes** | -- | Node to destroy. |

**Result:** Empty object `{}` on success.

```json
// Request
{
  "jsonrpc": "2.0",
  "method": "node/destroy",
  "id": 10,
  "params": {"node_id": "shell_a1b2c3d4"}
}

// Response
{
  "jsonrpc": "2.0",
  "id": 10,
  "result": {}
}
```

**Errors:**

| Error Code | Condition |
|------------|-----------|
| `NODE_NOT_FOUND` (-32000) | No node with the given ID exists. |

#### 4.2.5 `node/serialize` -- Serialize Node State

**Direction:** Host -> Server (request)

**Method:** `"node/serialize"`

Requests the full serialized state of a node for checkpoint or persistence
purposes. The returned data MUST be sufficient to reconstruct the node via
a corresponding deserialization mechanism (e.g., `from_dict()`).

**Params (NodeSerializeParams):**

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `node_id` | string | **Yes** | -- | Node to serialize. |

**Result (NodeSerializeResult):**

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `data` | object | No | `{}` | Full serialized state for reconstruction. |

The `data` object MUST include a `node_type` field for deserialization
dispatch.

**Errors:**

| Error Code | Condition |
|------------|-----------|
| `NODE_NOT_FOUND` (-32000) | No node with the given ID exists. |

### 4.3 Push Notifications (Server -> Host)

Push notifications are one-way messages from the server to the host. They
have no `id` field and expect no response.

#### 4.3.1 `node/dirty` -- Node State Changed

**Direction:** Server -> Host (notification)

**Method:** `"node/dirty"`

A one-bit signal indicating that a node's internal state has changed
asynchronously and the node needs synchronization. The host MUST mark the
node as dirty and include it in the next tick's sync cycle.

This notification carries no payload beyond the node ID. The full state is
retrieved during the subsequent `node/sync`.

Requires the `push_dirty` server capability. Servers that do not support
push notifications rely on the host polling via sync.

**Params (NodeDirtyParams):**

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `node_id` | string | **Yes** | -- | Node whose state changed. |

```json
{
  "jsonrpc": "2.0",
  "method": "node/dirty",
  "params": {"node_id": "shell_a1b2c3d4"}
}
```

#### 4.3.2 `node/notification` -- General Notification

**Direction:** Server -> Host (notification)

**Method:** `"node/notification"`

Delivers a notification from a node to the host. The host MUST propagate the
notification to the node's parent chain via the graph's notification system.

Requires the `push_notifications` server capability.

**Params (NodeNotificationParams):**

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `node_id` | string | **Yes** | -- | Source node. |
| `description` | string | **Yes** | -- | Human-readable description of what changed. |
| `level` | string | No | `"hold"` | Notification level (see below). |

**Notification levels:**

| Level | Semantics |
|-------|-----------|
| `"ignore"` | Informational only. The host MAY log it but SHOULD NOT wake the agent. |
| `"hold"` | Noteworthy change. The host SHOULD queue it for the agent's next turn. |
| `"wake"` | Urgent. The host SHOULD wake the agent if it is idle or waiting. |

```json
{
  "jsonrpc": "2.0",
  "method": "node/notification",
  "params": {
    "node_id": "shell_a1b2c3d4",
    "description": "Shell completed: pytest -v (exit 0)",
    "level": "wake"
  }
}
```

### 4.4 Host API (Server -> Host Requests)

The host API enables plugin servers to interact with the host's context graph.
These are requests from the server to the host (reverse direction). Each
message has an `id` field, and the host MUST respond.

Host API messages are OPTIONAL. The server SHOULD check the `host_capabilities`
received during initialization before sending these requests.

#### 4.4.1 `host/create_node` -- Create Node in Host Graph

**Direction:** Server -> Host (request)

**Method:** `"host/create_node"`

Requests creation of a child node in the host's context graph. Used for
nested node creation (e.g., a shell plugin creating artifact children for
output segments).

Requires the `create_node` host capability.

**Params (HostCreateNodeParams):**

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `node_type` | string | **Yes** | -- | Type of node to create (must be registered in host). |
| `args` | Any[] | No | `[]` | Positional constructor arguments. |
| `kwargs` | object | No | `{}` | Keyword constructor arguments. |
| `parent_id` | string | No | `""` | Parent node ID to link the new node to. |

**Result (HostCreateNodeResult):**

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `node_id` | string | **Yes** | -- | ID of the created node in the host graph. |

```json
// Server sends
{
  "jsonrpc": "2.0",
  "method": "host/create_node",
  "id": 100,
  "params": {
    "node_type": "artifact",
    "args": ["test output"],
    "kwargs": {"artifact_type": "output", "language": "text"},
    "parent_id": "shell_a1b2c3d4"
  }
}

// Host responds
{
  "jsonrpc": "2.0",
  "id": 100,
  "result": {"node_id": "artifact_x9y8z7w6"}
}
```

**Errors:**

| Error Code | Condition |
|------------|-----------|
| `NODE_TYPE_UNKNOWN` (-32001) | The requested node type is not registered in the host. |

## 5. Sync-on-Tick Model

CAP uses a tick-driven synchronization model. Rather than synchronizing state
on every mutation, changes are batched and applied at tick boundaries.

### 5.1 Tick Cycle

The host drives the tick cycle. A tick occurs at session-defined intervals
(typically once per agent turn, but MAY also occur on timer or event triggers).

At each tick:

1. The host collects all nodes that are **dirty** (either from `node/dirty`
   push notifications or from DSL method calls queued locally).
2. For each dirty node, the host sends one `node/sync` request containing
   all pending method calls for that node.
3. The server processes the calls in order, then returns the complete state.
4. The host updates its proxy node with the returned state, renders, tokens,
   digest, and notifications.
5. The host delivers any notifications to the graph's parent chain.

### 5.2 Dirty Flag Semantics

A node becomes dirty when:

- The server pushes a `node/dirty` notification (asynchronous state change).
- The DSL invokes a method on the node (queued as a PendingCall).
- The host explicitly marks the node for sync (e.g., after checkpoint restore).

The dirty flag is cleared after the `node/sync` response is processed.

### 5.3 Method Call Batching

Between ticks, the DSL MAY invoke multiple methods on the same node (e.g.,
`v.SetState(NodeState.ALL).SetTokens(500)`). These calls are accumulated as
a list of PendingCall objects and sent in a single `node/sync` request.

The server MUST process calls in array order. If a call fails, the server
SHOULD continue processing the remaining calls and report errors via the
state or notifications fields of the response.

This batching ensures that the hot path -- the projection build cycle --
requires at most one round trip per dirty node per tick.

### 5.4 One Round Trip Per Node Per Tick

The design invariant is: **at most one `node/sync` request per node per tick**.
This bounds the number of round trips to the number of dirty nodes,
regardless of how many method calls were queued.

### 5.5 Immediate Calls

For operations that cannot wait until the next tick (e.g., a DSL expression
that needs the return value immediately), the host MAY use `node/call`
instead of queuing. This bypasses the tick batching and executes the method
immediately.

`node/call` requires the `immediate_call` server capability. Servers that do
not support it MUST NOT receive `node/call` messages. If a server receives
`node/call` without declaring the capability, it SHOULD return a
`METHOD_NOT_FOUND` error.

If `node/call` sets `state_changed: true` in the response, the host SHOULD
mark the node as dirty for the next tick.

## 6. Schema Discovery

Node types are described by machine-readable schemas advertised during the
initialize handshake. Schemas enable code generation, validation, LLM
documentation, and autocompletion.

### 6.1 NodeTypeSchema

The top-level schema for a node type:

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `node_type` | string | **Yes** | -- | Type identifier (e.g., `"shell"`, `"topic"`). Must be unique per server. |
| `description` | string | No | `""` | Human-readable description for documentation and LLM prompts. |
| `constructor` | ConstructorSchema | No | empty | Constructor parameter schema. |
| `properties` | PropertySchema[] | No | `[]` | DSL-visible properties. |
| `methods` | MethodSchema[] | No | `[]` | DSL-callable methods. |

### 6.2 ConstructorSchema

Describes the constructor function using Python calling convention:

```
node_type(pos1, pos2, *variadic, named1=default1, named2=default2)
```

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `positional` | ParamSchema[] | No | `[]` | Positional parameters, in order. |
| `variadic` | ParamSchema or null | No | `null` | Variadic parameter (`*args`), if any. |
| `named` | ParamSchema[] | No | `[]` | Keyword-only parameters, with defaults. |

### 6.3 ParamSchema

Describes a single parameter:

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `name` | string | **Yes** | -- | Parameter name. |
| `type` | string | No | `"str"` | Type hint as a string (e.g., `"int"`, `"bool"`, `"list[str]"`). |
| `default` | Any | No | MISSING | Default value. See Section 6.3.1. |
| `description` | string | No | `""` | Human-readable description. |

#### 6.3.1 The MISSING Sentinel

A parameter with no default value is represented by the absence of the
`default` field in the wire format. Implementations MUST distinguish between:

- `default` field absent: parameter is **required**, no default value.
- `default` field present with value `null`: parameter is optional with
  default value of `null`.

In the reference implementation, the `MISSING` singleton represents this
distinction in memory.

### 6.4 PropertySchema

Describes a DSL-visible property:

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `name` | string | **Yes** | -- | Property name (e.g., `"is_complete"`, `"output"`). |
| `type` | string | No | `"Any"` | Type hint as a string. |
| `readable` | boolean | No | `true` | Whether the DSL can read this property. |
| `writable` | boolean | No | `false` | Whether the DSL can assign to this property. |
| `description` | string | No | `""` | Human-readable description. |

Properties with `readable: true` are accessible via attribute access in the
DSL (e.g., `node.is_complete`). Properties with `writable: true` support
assignment (e.g., `node.output = "..."`).

### 6.5 MethodSchema

Describes a DSL-callable method:

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `name` | string | **Yes** | -- | Method name (e.g., `"cancel"`, `"set_content"`). |
| `params` | ParamSchema[] | No | `[]` | Method parameters (excluding `self`). |
| `returns` | string | No | `"None"` | Return type hint as a string. |
| `description` | string | No | `""` | Human-readable description. |
| `chainable` | boolean | No | `false` | If `true`, method returns `self` for fluent chaining. |

Chainable methods return the node proxy, enabling patterns like:

```python
v.SetState(NodeState.ALL).SetTokens(500).Run(TickFrequency.turn())
```

## 7. Capabilities

Capabilities are feature flags exchanged during the initialize handshake. They
allow hosts and servers to operate at the intersection of their supported
features, enabling graceful degradation when a peer does not support an
optional feature.

### 7.1 HostCapabilities

Declared by the host in the `initialize` request. Tells the server which host
API features are available.

| Capability | Type | Default | Description |
|------------|------|---------|-------------|
| `create_node` | boolean | `true` | Host supports `host/create_node` for child node creation. |
| `invoke` | boolean | `true` | Host supports `host/invoke` for method calls on host nodes. |
| `roots` | boolean | `true` | Host supports `host/query_roots` and `host/resolve_root`. |
| `notifications` | boolean | `true` | Host accepts `node/dirty` and `node/notification` push. |

If a capability is `false`, the server MUST NOT send the corresponding
messages. If the server does send them, the host SHOULD respond with
`PERMISSION_DENIED` (-32004).

### 7.2 ServerCapabilities

Declared by the server in the `initialize` response. Tells the host which
synchronization features the server supports.

| Capability | Type | Default | Description |
|------------|------|---------|-------------|
| `sync` | boolean | `true` | Server supports `node/sync` (tick-based synchronization). |
| `immediate_call` | boolean | `false` | Server supports `node/call` (immediate method execution). |
| `push_dirty` | boolean | `true` | Server pushes `node/dirty` notifications. |
| `push_notifications` | boolean | `true` | Server pushes `node/notification` messages. |

If `sync` is `false`, the host MUST NOT send `node/sync` messages. The host
MUST use `node/call` (if `immediate_call` is `true`) or rely on state from
`node/create` responses only.

If `immediate_call` is `false` (the default), the host MUST NOT send
`node/call` messages. All method calls MUST be batched through `node/sync`.

### 7.3 Capability Negotiation

The negotiation process is:

1. Host sends `initialize` with its `host_capabilities`.
2. Server reads the capabilities to determine which host API methods it can
   use.
3. Server responds with its `server_capabilities`.
4. Host reads the capabilities to determine which node management methods it
   can use.

There is no further negotiation after initialization. Capabilities are fixed
for the lifetime of the connection.

**Minimal viable server**: A server that declares all capability defaults
(`sync: true`, `immediate_call: false`, `push_dirty: true`,
`push_notifications: true`) supports the standard sync-on-tick model and
push notifications. This is the RECOMMENDED default configuration.

**Minimal viable host**: A host that declares all host capabilities as `true`
enables the full range of server interactions. This is the RECOMMENDED default.

## 8. Error Model

CAP uses the JSON-RPC 2.0 error response format for all error conditions.

### 8.1 Error Response Format

```json
{
  "jsonrpc": "2.0",
  "id": 5,
  "error": {
    "code": -32000,
    "message": "Node not found: shell_a1b2c3d4",
    "data": {"node_id": "shell_a1b2c3d4"}
  }
}
```

The `error` object contains:

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `code` | integer | **Yes** | Numeric error code (see Section 8.2). |
| `message` | string | **Yes** | Human-readable error description. |
| `data` | Any | No | Additional structured error data. |

### 8.2 Error Codes

#### Standard JSON-RPC 2.0 Errors

| Code | Name | Description |
|------|------|-------------|
| -32700 | `PARSE_ERROR` | Invalid JSON received. |
| -32600 | `INVALID_REQUEST` | JSON is not a valid JSON-RPC request. |
| -32601 | `METHOD_NOT_FOUND` | The method does not exist or is not available. |
| -32602 | `INVALID_PARAMS` | Invalid method parameters. |
| -32603 | `INTERNAL_ERROR` | Internal server error. |

#### CAP-Specific Errors (Reserved Range: -32000 to -32099)

| Code | Name | Description |
|------|------|-------------|
| -32000 | `NODE_NOT_FOUND` | No node instance with the given ID exists. |
| -32001 | `NODE_TYPE_UNKNOWN` | The requested node type is not registered. |
| -32002 | `METHOD_NOT_AVAILABLE` | The method is not defined on this node type, or requires a capability not declared. |
| -32003 | `ROOT_NOT_FOUND` | The filesystem root URI does not match any known root. |
| -32004 | `PERMISSION_DENIED` | The operation is not permitted (capability not declared, sandbox violation, etc.). |
| -32005 | `NODE_CREATE_FAILED` | Node creation failed (invalid arguments, resource exhaustion, etc.). |

### 8.3 Recovery Semantics

Error recovery depends on the error category:

**Transient errors** (INTERNAL_ERROR, NODE_CREATE_FAILED): The host MAY retry
the operation. The server's state is unchanged -- the failed operation had no
side effects.

**Permanent errors** (NODE_NOT_FOUND, NODE_TYPE_UNKNOWN, METHOD_NOT_AVAILABLE):
The host SHOULD NOT retry with the same parameters. The host SHOULD log the
error and report it to the agent.

**Protocol errors** (PARSE_ERROR, INVALID_REQUEST, INVALID_PARAMS): These
indicate a bug in the sender. The host or server SHOULD log the error for
debugging. The connection MAY continue operating.

**Permission errors** (PERMISSION_DENIED, ROOT_NOT_FOUND): The sender
attempted an operation the receiver does not support. The sender SHOULD check
capabilities before retrying.

**Connection loss**: If the transport connection is lost unexpectedly, all
pending requests MUST be resolved with errors. The host SHOULD transition
to the `ERROR` state and MAY attempt reconnection.

## 9. Security Model

CAP operates within a sandboxed security model that constrains what plugin
servers can access and do.

### 9.1 Roots-Based Filesystem Access

The host exposes filesystem access through named roots (see RootInfo in
Section 4.1.1). Plugin servers:

- MUST use `host/query_roots` and `host/resolve_root` to discover and resolve
  filesystem paths.
- MUST NOT access filesystem paths outside the declared roots unless
  explicitly permitted by the host's permission system.
- SHOULD use normalized paths relative to roots rather than absolute paths
  when communicating with the host.

### 9.2 Permission Boundaries

The host's permission system (PermissionManager) governs all access:

| Boundary | Enforcement |
|----------|-------------|
| **File access** | Plugin filesystem operations go through the host's roots and permission checks. Direct file access by the plugin process is outside CAP's control but SHOULD be constrained by OS-level sandboxing. |
| **Node creation** | The `host/create_node` capability and `PERMISSION_DENIED` error enforce authorization for graph modifications. |
| **Method invocation** | The `host/invoke` capability constrains cross-node method calls. The host MAY apply additional method-level permissions. |
| **Capability gating** | All host API operations are gated on the corresponding `host_capabilities` flag. |

### 9.3 Sandboxing Considerations

Plugin servers run as separate processes. Hosts SHOULD consider:

- **Process isolation**: Run plugin servers with minimal OS privileges.
- **Resource limits**: Apply CPU, memory, and I/O limits to plugin processes.
- **Network access**: Plugin servers SHOULD NOT have network access unless
  explicitly required and declared.
- **Secrets**: The host MUST NOT pass secrets to plugin servers via initialize
  params or environment variables unless the plugin is trusted. Use the
  host's secret management system (e.g., `fetch_secret()`) instead.
- **Input validation**: Both host and server MUST validate all incoming
  message parameters before processing.

### 9.4 Trust Model

CAP assumes a trust hierarchy:

1. The **host** is trusted -- it owns the graph, drives the tick cycle, and
   controls process spawning.
2. **Plugin servers** are semi-trusted -- they run in separate processes with
   capability-gated access to host resources.
3. The **agent** (LLM) is untrusted -- its DSL calls go through the host's
   permission system before reaching plugin servers.
